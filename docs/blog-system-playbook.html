Blog system playbook

A reusable rule set for standing up a content-marketing blog on a static site + Cloudflare Pages + Astro, with SEO baked in and daily auto-publish. Written from building trady360.com/blog — apply directly to another app by swapping the domain, brand tokens, and content topics.

1. Domain architecture

Merge the blog into the main marketing site's Cloudflare Pages project — don't give it its own subdomain or project. A separate blog.example.com or a standalone Pages project splits domain authority; Google treats a path (example.com/blog) as part of the same site, a subdomain as a weaker signal.

  • Build the blog (Astro, output: 'static') as its own app in the repo.
  • In the marketing site's deploy step, after its own static files are copied, merge the blog's dist/ into the marketing site's dist/ — copy the tree in without clearing the destination first (a plain cp -r/fs.cpSync merge, not the same "clear then copy" helper used for the marketing site's own files, or it'll delete everything already staged).
  • Result: one Cloudflare Pages project, one custom domain, /blog and /vi/blog (or whatever locale prefix) living next to /pricing, /features, etc.

2. Bilingual content (skip if single-language)

  • Content collection files live in per-locale subfolders: content/blog/en/*.md, content/blog/vi/*.md. The entry slug is en/foo / vi/foo — strip the prefix for the public URL.
  • Routes: /blog/[slug] for the default locale (no prefix), /{locale}/blog/[slug] for others.
  • Don't assume the same slug in both languages. Add an explicit altSlug field in frontmatter pointing at the sibling's bare slug, and only render hreflang alternate links when that sibling post actually exists in the other language's collection (check both title-wise — don't just assume symmetry).

3. Draft-based publish queue (this is what makes daily automation safe)

Add draft: boolean (default false) to the content collection schema. Every page's getCollection() call filters !data.draft. Write posts ahead of time with draft: true; a separate mechanical step flips one post's draft to false and bumps its date on the day it should go live.

This decouples writing (needs judgment, should be reviewed) from publishing (mechanical, safe to automate). Keep a content-queue.json tracking {id, status: pending|published, slugVi, slugEn, catalog...} — the publish step just needs to find the first pending item.

4. SEO baseline — do this once, every post inherits it

  • @astrojs/sitemap integration. Pin the version to what your Astro major supports — the sitemap package's newer majors require Astro 5 integration hooks and fail silently/crash on Astro 4.
  • robots.txt with Sitemap: https://{domain}/sitemap-index.xml.
  • Canonical URL: if the build uses directory format (path/index.html), every page serves at a trailing-slash URL. Build canonical/hreflang URLs with a trailing slash too, or you get an unnecessary redirect hop and a canonical tag that points at a redirecting URL.
  • Article JSON-LD per post (headline, description, datePublished, author, publisher, inLanguage).
  • GA4: reuse the existing measurement ID from the main app if there is one — one property across the whole domain beats fragmenting analytics per subsection.

5. Design system — pull real brand tokens, don't accept scaffold defaults

Starter templates default to generic colors (Stripe-blue-green) and Inter. Before shipping, swap in the actual brand palette and typefaces from the brand guideline, even if that means grepping an old PDF/brand doc for hex values. A blog that doesn't match the product's brand reads as an afterthought.

Layout patterns that read as "designed" rather than "scaffolded":

  • Dark, high-contrast hero section on the homepage/catalog pages showing the featured post's real image — not a gradient placeholder.
  • Image-card grid for post listings (not a plain stacked text list). Share this grid's CSS between the homepage and every catalog/tag page so they read as one system.
  • A serif or display face for headlines paired with a plain sans for body — cheap way to look considered instead of generic.

6. Content style rule — emphasis, not decoration

Document a small, enforced budget for inline color emphasis in article bodies (e.g. 3 semantic spans: wrong-behavior/red, right-behavior/green, key-insight/gold), with a hard cap like 3–6 highlighted spans per post, 2–6 words each, never a whole sentence. Without a stated budget, either nothing gets highlighted (bland) or everything does (noise, no signal). Write it down once (CONTENT-STYLE.md) so every future writer — human or agent — follows the same rule.

7. Sourcing images without a real design budget

  • If the team already has an AI-illustration library (Gemini/ChatGPT image history) in a consistent style, reuse those before generating anything new — check the library/gallery view for titles matching the post's topic before spending time on prompts.
  • Browser-automating an image download: use element refs (via a find-then-click pattern), not fixed pixel coordinates. Coordinates break as soon as a chat has multiple turns or the layout shifts by a few px; a find("download button inside the lightbox") → click-by-ref is far more reliable, at the cost of one extra tool round-trip.
  • For fully automated/headless publishing (a cloud cron with no browser), don't attempt image generation at all. Commit a static SVG fallback template matching the brand palette to the repo; the automation just copies that file verbatim when a post has no image: field. Zero external dependencies, always works.

8. Daily auto-publish via cloud cron

  • The mechanical publish step (flip draft, bump date, fallback image if missing, build, commit, push) is small enough to hand to a scheduled cloud agent — but it needs git, not a local deploy script, because the agent runs in an isolated sandbox with no access to the machine that has your CDN/hosting credentials.
  • Wire CI (e.g. GitHub Actions) to auto-deploy on push to main, scoped by path (paths: ["apps/blog/**", ...]) so unrelated pushes to other parts of the monorepo don't trigger a production deploy.
  • Before relying on this: verify the cloud agent actually has GitHub access (a real blocker the first time — GitHub App install alone wasn't enough, the platform account itself needed a separate "connect GitHub" step). Check the routine's run history periodically — ours silently failed for 4 days straight because the org disabled Claude subscription access for cloud routines; nothing on the blog side was broken, but zero posts published until we caught it.
  • Cron timing: pick a local time, convert to UTC yourself, confirm the math with the person who asked (DST-naive humans get this wrong constantly).

9. Deploy discipline

Decide explicitly, in writing, whether interactive changes get committed to git or just deployed directly — and hold the line once decided. Deploying straight to the CDN without committing is fine and fast for solo iteration, but breaks any automation that reads repo state (a queue file, a "what's already published" check) — that automation will drift from what's actually live. If you choose deploy-only, accept that drift is now a manual-tracking problem, or keep the two paths (content-queue commits vs. presentation-only deploys) explicitly separate instead of blanket-applying one rule to both.

10. Lead-gen / community CTA

A single, consistent "talk to us" block at the end of every article (support email + community channel link) costs one component and one import per template — cheap, and it's the only conversion point most readers of an educational post will ever see.

11. Before starting on someone else's repo

  • Read the project's own CLAUDE.md/contributor doc first — it may mandate a task-tracking file (PLAN.md), a debug-log convention, or a "propose a decision file before ambiguous work" rule. Follow it or explicitly ask to skip it for out-of-scope work (a blog is often outside a repo's primary tracked surface).
  • Run git status before any multi-file commit. A repo that's been worked on by multiple sessions/people can have unrelated staged changes (in our case, a half-finished homepage rename) sitting in the index — stage and commit only the paths you actually touched, never git add -A.
